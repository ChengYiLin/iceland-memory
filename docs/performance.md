# 地圖初始化效能

## 地圖程式與圖資是兩種成本

Vue 管理畫面與互動，MapLibre GL JS 負責繪製與鏡頭，OpenFreeMap 提供底圖。MapLibre 依視野請求圖磚，並未下載整個世界；只看冰島能減少不必要的圖資，不能直接裁掉地圖引擎本身。

目前正式建置的 JavaScript 合計約 1.67 MB，包含獨立 worker。測試用 Node 壓縮後約為 gzip 0.47 MB、Brotli 0.38 MB；這是檔案壓縮測試，Vite preview 沒有啟用這些傳輸壓縮。正式部署應由 CDN／託管平台提供壓縮與快取。

開發模式曾量到約 10.2 MB JavaScript、約 6.5 秒才出現日期標記，是單次樣本。開發模式包含未壓縮程式與開發工具，不應用來代表上線表現。

## 修改與實測

2026-10-24，Vue 3.5.44、MapLibre GL JS 6.15.0。使用相同 Chromium、1440 × 900 視窗、每次全新隔離 context 並停用快取，交錯量測修改前後正式建置各三次。沒有網路或 CPU 限速；本機負載與外部圖資網路仍會造成波動。

| 指標                         | 修改前        | 修改後        |
| ---------------------------- | ------------- | ------------- |
| 初始圖磚請求數               | 12            | 4             |
| 外部底圖資源，解壓後         | 656,280 bytes | 364,130 bytes |
| 日期標記出現，中位數         | 5.02 秒       | 0.63 秒       |
| 首輪底圖載入提示消失，中位數 | 5.02 秒       | 3.75 秒       |

0.63 秒表示日期標記可操作，不代表完整底圖已畫完。底圖完成是以 MapLibre 首次 `load` 事件解除提示作為量測點，未計入後續操作造成的新圖磚。時間是本機小樣本，不是上線速度保證；較穩定的結果是圖資量減少約 45.5%，圖磚請求減少約 66.7%。

交錯測試原始時間：修改前標記與底圖為 5.02、4.89、9.85 秒；修改後標記為 0.56、0.63、0.68 秒，底圖為 3.75、4.15、3.73 秒。較早的另一輪修改前中位數只有 1.66 秒，因此不可混用不同輪次宣稱提升倍數。

| 調整                                    | 結果與決定                                                                             |
| --------------------------------------- | -------------------------------------------------------------------------------------- |
| 初始鏡頭直接設定冰島範圍                | 圖磚 12 → 4、外部資源 656 → 364 KB，保留。單獨測試的時間波動大，不據此宣稱加速。       |
| `style.load` 時建立回憶與日期入口       | 不等待全部圖磚與字體；交錯測試中位 5.02 → 0.63 秒，保留。完整底圖提示仍等首次 `load`。 |
| 限制探索區域、最大縮放 12、關閉世界重複 | 符合冰島主題，避免不必要的遠方與過細探索；不把它算成 JS 減量。                         |

## 重測

先安裝 Chromium，建置並啟動正式預覽，再從另一個終端量測。

```sh
nvm use
npx playwright install chromium
npm run build
npm run preview -- --host 127.0.0.1
# 另一個終端
npm run perf:map
```

可指定網址、報告路徑與次數：

```sh
npm run perf:map -- http://127.0.0.1:4173/ test-results/map-performance.json 3
```

報告包含頁面繪製、日期標記、底圖載入、請求與解壓後資源大小。圖磚數以目前服務的 Z/X/Y 路徑辨識，替換圖資格式後應調整辨識方式。跨來源實際傳輸大小與真實使用者速度應另用部署後監測驗證。

瀏覽器回歸測試會刻意延遲底圖來源，確認日期標記能先出現並切換一天；這可防止程式再次將回憶操作綁在完整底圖完成之後，而不依賴容易波動的秒數門檻。

## 地圖方案取捨

| 方案           | 適合本專案的部分                                       | 需要承擔的取捨                                                           |
| -------------- | ------------------------------------------------------ | ------------------------------------------------------------------------ |
| MapLibre GL JS | 可調整向量底圖風格、平順鏡頭與縮放，可持續擴充路線視覺 | 引擎與 worker 有固定成本，需要 WebGL；區域裁切不會縮小引擎               |
| Leaflet        | 2D 縮放、標記、照片、線段已能滿足核心需求，函式庫較輕  | 一般點陣底圖的外觀由圖資決定；向量圖磚需額外方案，細緻敘事動畫自行組合   |
| Mapbox GL JS   | 向量地圖、設計與商業服務整合                           | 需要 access token 與留意服務計費；更換不保證初始化變快                   |
| OpenLayers     | 資料格式、投影與 GIS 操作完整                          | 目前故事地圖尚未需要這些能力，選用要有具體需求                           |
| 自製冰島 SVG   | 島嶼輪廓、路線、回憶點可整體設計，資料可以僅限冰島     | 地名、道路、不同縮放層級的細節需要自己準備，不能只換掉引擎就保有完整底圖 |

目前先保留 MapLibre 的地圖體驗。若重視極小的 2D 程式成本，可以再用相同旅程做 Leaflet 對照，實測後選擇。若決定只要插畫式島嶼與路線，自製 SVG 值得優先評估。

若仍保留完整地圖且要自行控制圖資，可製作冰島範圍的 PMTiles，放在支援 HTTP Range 的儲存服務；瀏覽器只讀取需要的圖磚，無須一次下載整個檔案。它帶來圖資製作、樣式、字體與託管管理成本，且不保證比現在的區域圖磚更快，因此尚未導入。
